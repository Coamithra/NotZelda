# Combat, Monsters & Netcode

Detailed implementation notes for combat mechanics, monster behavior, and the netcode stack.

## Sword & Attack

- **Sword hitbox**: 1.0 tile in the attack direction (0.25 back into player + 0.75 forward), `SWORD_PERP_WIDTH` (0.6) tiles perpendicular (centered on player body). Computed by `sword_hitbox()` in `commands.py` (single source of truth — also used by `/viewserver` debug overlay). Narrowed from 1.0 to prevent corner-camping exploits now that monster positions are continuous. The hitbox stays active for `SWORD_ACTIVE_DURATION` (180ms, ~5 ticks) after the swing — `sword_hit_scan()` runs each tick, tracking already-hit monsters by `id(monster)` so each is only damaged once per swing. `player.active_attack` holds the swing state (direction, start_time, room, anchor position, hit set); `_tick_active_attacks()` in `combat.py` drives the per-tick scans. Attack is carried in the `player_state` frame as `attacking: {direction, x, y}` — the server detects the false→true edge via `Avatar.last_reported_attacking` and calls `_initiate_attack()` in `commands.py`, which sets up `active_attack` and runs the first `sword_hit_scan()`. Client-supplied `x`/`y` anchors the hitbox to the client's exact position. Other players see attacks via `player_state_update`; late joiners via `player_info()`. `ATTACK_COOLDOWN` (300ms) matches client animation (150ms × 2 frames) — cooldown check has one `TICK_INTERVAL` of tolerance to absorb tick alignment jitter.
- **Attack cooldown gap**: 90ms `attack_cooldown` client state between sword swings (`ATTACK_GAP_MS` in `renderer.js`). Player can't move or attack during the gap. Creates a vulnerability window between swings. Under review (Trello #88).
- **Player-vs-monster collision**: player hitbox is inset by `PLAYER_COLLISION_MARGIN` (0.2) per side, making a 0.6×0.6 AABB for contact damage. Smaller box replaces the old grace period for corner-scrape forgiveness. Shown in `/viewserver` overlay as bright red inset within faint red full tile.
- **Combat constants tuned**: `ATTACK_COOLDOWN` = 0.27s (was 0.3), `COLLISION_GRACE_PERIOD` = 0.0s (removed — smaller hitbox handles it). `SWORD_PERP_WIDTH` = 0.6 (was implicit 1.0). `PLAYER_COLLISION_MARGIN` = 0.2. `MOVE_STEP` = 1.0 (full-tile monster movement).

## Monster Behavior

- **Boss monsters** have `"boss": True` in their stats dict. Use `monster.is_boss` — never hardcode boss checks to a specific kind. Boss sprites use `"resolution": 2` in their sprite data for higher detail density — coordinates are in a 32x32 grid instead of 16x16, and `drawMonsterSprite`/`drawMonsterDeath`/`renderCorpses` divide scale by resolution so each unit maps to the same pixel size as normal sprites.
- **Boss hit behavior**: non-knockbackable monsters (bosses) take damage but do NOT have their current action interrupted — charge/aoe windups continue through hits. Controlled by `monster.knockbackable` check in `commands.py` hit handling.
- **Monster knockback**: controlled by `monster.knockbackable` (from `"knockback"` in monster stats, defaults to `true` for non-bosses, `false` for bosses). Knockbackable monsters get pushed 1 tile in the attack direction when hit (if they survive). Knockback is **server-side simulated** — `monster.state = "knockback"` with easeOutQuad interpolation over `KNOCKBACK_DURATION` (0.2s) in `_tick_all_monsters`. The `monster_hit` message includes `knock_from_x/y` and `knock_duration` for client dead reckoning. Every hit resets the decision timer and interrupts the current action (walk/charge/etc.), even if the monster can't be knocked back due to a wall. Non-knockbackable monsters (bosses, heavy monsters) take damage but continue their behavior script uninterrupted.
- **Monster pack sizes**: `pack_min`/`pack_max` in `data/monsters.json` define the "challenging" count range per monster type (from gauntlet testing). Bat: 10-13, skeleton: 3-5, phantom: 3-4, dungeon_slime: 2-3, water_serpent: 3-5, drowned_one: 2-3. Loaded into `game.monster_stats` at startup. All monsters should have pack sizes — default fallback is 3-5 for unknown types.
- **Dynamic monster groups (pack fractions)**: dungeon room templates use `monsters <kind> <fraction>` (plural) for dynamically-placed monsters. Fraction is a float where 1.0 = a full pack of that type. All fractions in a room must sum to 1.0. At room resolution, `_resolve_dynamic_monsters()` in `dungeons.py` converts fraction to count via `fraction × randint(pack_min, pack_max)`, then scales by difficulty tier, and `_find_monster_positions()` places them on valid walkable tiles with spacing. Old `monster <kind> <x> <y>` (singular) still works for fixed-position placement (boss rooms, overworld rooms). AI-generated rooms also use pack fractions via `monster_groups` (not `monster_placements`); the AI auto-patcher normalizes fractions to sum to 1.0.
- **Monster barrier tiles**: `MB` tile in `tiles.json` — visually identical to grass, `walkable: true` (players pass through), `monster_walkable: false` (monsters blocked). `game.is_monster_walkable_tile()` in `state.py` checks `monster_walkable` property, falls back to `walkable`. Behavior engine's `_is_walkable()` uses the monster-specific check. Used in `clearing.room` to fence the slime to the bottom half.
- **Guard despawn constants**: `GUARD_DESPAWN_TIMEOUT`, `GUARD_DESPAWN_DISTANCE`, `GUARD_DESPAWN_GRACE` live in `constants.py`. Use `_despawn_guards(guards, room_id, msgs)` helper in `combat.py` to kill all guards in a list.

## Monster Movement

- **Monster walk state**: `WalkState` dataclass in `models.py` holds walk data (from/to positions, walk_time, timing, direction). Assigned to `monster.state_data` when `state == "walking"` — access via `sd.from_x`, not `sd["from_x"]`. `sd.walk_time` is the actual step duration (base `monster.walk_time` scaled by step distance). Other states (charging, teleporting, area) still use plain dicts. `state == "knockback"` uses a plain dict with `from_x/y`, `to_x/y`, `start_time`, `duration`.
- **Continuous monster movement**: monsters move in full-tile steps (`MOVE_STEP = 1.0`). `_is_walkable_at()` in `behavior_engine.py` checks all tiles covered by a float-position footprint. Monster positions are interpolated every tick during walks and knockbacks. Error recovery snaps to nearest integer tile (`round(x)`).
- **Monster walk collision**: server updates `monster.x/y` to the interpolated position **every tick** during a walk and checks contact collision continuously. Dodge window is natural (move out of the monster's path) rather than artificial checkpoints. `WalkState.walk_time` stores the actual duration for the step (scaled by distance).

## Server-Authoritative Netcode

- **Player movement is server-authoritative**: client sends `player_input` messages (batched at ~30fps) containing input frames `{seq, dir, dt}` plus a top-level `atk` flag. Server runs the same movement simulation (`_simulate_player_move` in `commands.py`) — speed, half-tile axis snapping, collision with fallback — and sends `state_correction` messages back with `{ack_seq, x, y}`. Client predicts locally via `simulateMove()` (pure function in `client.html`), keeps an `inputBuffer` of unacked inputs, and on correction replays them from the server position. Visual drift is absorbed by `correctionOffset` (decays per frame via `CORRECTION_RATE`). Packets are always sent at 30fps even when idle so the server sees clean attack edge transitions. Legacy `player_state` (position-based) handler still exists for backward compat but new clients use `player_input`.
- **Entity interpolation (remote players)**: other players are rendered ~66ms behind real-time (`INTERP_DELAY`). Each remote player has a `snapshots` ring buffer (max `INTERP_BUFFER_SIZE = 6`) of `{x, y, dir, t}` entries pushed on `player_state_update`. The gameLoop lerps between the two snapshots bracketing `now - INTERP_DELAY`. When no new snapshots arrive (player stopped), freezes at last known position (no extrapolation — TCP guarantees delivery).
- **Lag compensation (combat)**: `sword_hit_scan()` rewinds monster positions by the player's RTT when testing hitbox collision. Monster position history is recorded every tick in `_tick_all_monsters()` (`monster.position_history` deque, maxlen=10). RTT is measured client-side via ping/pong timestamp echo (`G.conn.rtt`), sent in `player_input` messages, stored as `player.rtt` (capped at `LAG_COMP_WINDOW = 200ms`). Hit detection uses rewound positions; damage/knockback uses current positions.
- **RTT measurement**: client includes `ct: performance.now()` in ping messages, server echoes it in pong. Client computes `G.conn.rtt = now - ct` on receipt. Server receives client-reported RTT in `player_input.rtt` (ms), converts to seconds and caps at 200ms.
- **Dead reckoning (monster actions)**: client-side monster prediction via `effectiveDuration = serverDuration - RTT/2`. All monster visual state uses a unified `monster.action` object with `{type, startTime, effectiveDuration, duration, seq, ...typeParams}`. Action types: `walk` (lerp position, converge at 100%), `knockback` (easeOutQuad, skip-ahead strategy), `charge_warmup`/`teleport_warmup`/`area_warmup` (drive visual effects, no position change). `monster.correctionOffset` (decays per frame by `MONSTER_CORRECTION_RATE`) absorbs visual discontinuities on walk start. Warmup durations sent from server: `charge_prep.duration`, `teleport_start.delay`, `area_warning.duration`. Warmup rendering iterates `G.room.monsters` by action type (replaced `G.fx.chargePreps` and `G.fx.areaWarnings`). `G.fx.chargeTrails` stays as fire-and-forget. `computeEffectiveDuration()` in `net.js` clamps minimum to 16ms.

## Player Position & Movement

- **Player position model**: single canonical position on `G.player.myPlayer.x/y`. `G.player.displayX/Y` is computed each frame as `myPlayer.x/y + knockbackOffsetX/Y`. No separate `preciseX/Y`. Knockback sets `knockbackOffsetX/Y` (visual offset from old position, decays to 0 over 200ms via easeOutQuad). Player input is blocked during knockback (`knockbackSlide` guard in `playerTick()`). Other players and monsters still use `from/to` knockbackSlide interpolation.
- **Stair re-trigger guard**: `Avatar.spawn_stair` tracks the stair tile a player spawned on after a room transition. Stair detection is skipped until the player moves off that tile, preventing infinite transition loops with continuous position updates.

## Debug Tools

- **Debug /viewserver**: sends full `debug_state` snapshot every tick to subscribed players (toggled via `/viewserver` chat command, debug-only). Renders semi-transparent red shapes for server-side entity positions.
- **Admin `/admin/library-stats`**: password-protected HTTP endpoint returning JSON snapshot of content library composition (per-dungeon real/permanent/custom/placeholder counts), deprecated content, and API usage (tokens, cost, rate limits). Gated behind `ADMIN_PASSWORD` env var — returns 404 if unset, requires HTTP Basic Auth (`admin:<password>`) if set. Works in both debug and production. Built by `_build_library_stats()` in `mud_server.py`.
- **The Gauntlet** (debug-only): monster difficulty tuning arena in `server/gauntlet.py`. `/gauntlet [kind] [count]` creates a linear dungeon of trap rooms with the specified monster type. `/gt <param> <value>` tunes stats (walk_time, decision_time, damage, hp, count, plus rule-level params like warmup, cooldown, range, drift, damage_radius). `/gt hard` resets to max difficulty; `/gt halve` bisects toward defaults. Auto binary-search adjusts one random param per wave based on outcome (EASY/GOOD/HARD/TOO HARD). Death = wave over (advances to next room). Results logged to `gauntlet_results.txt` (append-only). Heart drops disabled in gauntlet for clean damage tracking. Session state in `_sessions` dict, cleaned up on `/gauntlet stop`, room exit, or disconnect.
- **`log` message type**: client-side chat-log-only message (no popup overlay). Used for monster kill messages to reduce visual clutter. Handler in `net.js`.
- **Room geometry constants** live in `server/constants.py`: `DOORWAY_TILES`, `ALL_DOORWAY_TILES`, `bfs_reachable()`. Use `bfs_reachable()` instead of inline BFS for tile reachability checks.
