# Architecture Reference

Detailed module descriptions for the NotZelda MUD. For rules, gotchas, and quick reference, see `CLAUDE.md`.

## Client (`client/`)

All client-side state lives on a shared `G` namespace object (defined in `game_state.js`, loaded first). Constants (`TILE`, `SCALE`, `TS`, `COLS`, `ROWS`, `CW`, `CH`, `MOVE_LERP`) are plain globals. Script load order in `client.html` matters: `game_state.js` → `title.js` → `tiles.js` → `sprite_data.js` → `sprites.js` → `music.js` → `renderer.js` → `fx.js` → `net.js` → inline init/gameLoop → `input.js`.

- **`client/client.html`** — HTML + CSS + inline init script. Login overlay, mobile detection, DOM ref binding to `G`, `processMovement()`, `gameLoop()`. Loads all other JS files via `<script>` tags. Includes `#server-log` panel (340px sidebar, shown in debug mode) for live server log streaming with color-coded lines (regen=green, deprecation=purple, dungeon=gold, errors=red).
- **`client/game_state.js`** — Constants and the `G` namespace object holding all mutable state (ws, myName, myPlayer, otherPlayers, currentRoom, monsters, projectiles, keysDown, animation timers, etc.).
- **`client/renderer.js`** — All `render*()` functions (room, players, speech bubbles, UI, HUD, transitions, projectiles, area warnings, charge effects, death animations, sword/heart pickups). All `update*()` functions (dances, attacks, dying monsters/players, projectiles, attack effects). Helper functions (`startDance`, `stopDance`, `startAttack`, `getExitDirs`, `roundRect`).
- **`client/net.js`** — WebSocket connection (`connect()`, `scheduleReconnect()`), `handleMessage()` switch for all server message types, `dbg()` debug logger.
- **`client/input.js`** — Keyboard handlers (keydown/keyup), chat input focus/blur/submit, login button, visibility change reconnect, mobile joystick touch handlers, mobile chat/sword buttons, debug toggle. Must load last (after DOM refs are bound and all functions defined).
- **`client/sprite_data.js`** — Declarative sprite definitions. All NPC, monster, death animation, player dance/walk/fall sprites defined as data arrays of `[colorKey, x, y, w, h]` layers. Color keys resolve via sprite-local colors > `PALETTE` globals > literal hex. Monster data includes per-frame hop offsets. Special effects (bob, alpha, pulse glow) declared as `effects` on the sprite entry. Also defines `customMonsterSprites` and `customDeathSprites` runtime registries for AI-generated monster sprites (populated from server data at room entry).
- **`client/sprites.js`** — Sprite renderer + remaining procedural sprites. Core `drawLayers()` function renders data from `sprite_data.js`. `drawNPCSprite()` handles effects (bob, alpha, pulse). `drawMonsterSprite()`/`drawMonsterDeath()` handle frame selection and yOff, checking both static `MONSTER_SPRITE_DATA`/`DEATH_SPRITE_DATA` and the custom runtime registries. `drawMonsterDeath()` auto-generates a generic splat from the monster's primary color if no death sprite exists. Player sprites use `SHIRT` color placeholder resolved at draw time via `makePlayerColorMap()`. Attack/sword/heart sprites remain procedural (dynamic offsets). All original function names preserved as backward-compatible wrappers.
- **`client/tiles.js`** — Data-driven tile rendering using rect layers (same `[colorKey, x, y, w, h]` format as sprites). `TILE_COLORS` defines per-tile color palettes. `TILE_SPRITE_DATA` defines each built-in tile as an array of rect layers drawn on top of the base color fill. `drawTileLayers()` renders the layers. `createTileCanvas()` fills base color then draws layers. Cached to offscreen canvases. Exposes `getTileCanvas(tileId, TS, TILE, SCALE)` and `TILE_COLORS`. Also defines `customTiles` runtime registry and `runTileRecipe()` interpreter for AI-generated tiles — recipes are JSON objects with named colors and a `layers` array of `[colorKey, x, y, w, h]` rects. `getTileCanvas()` checks `customTiles` for string tile IDs before falling back to static data.
- **`client/music.js`** — Background music. MP3 playback with crossfade. Server sends a `music` field per room (e.g. `village`, `tavern`, `chapel`, `overworld`, `dungeon1`–`dungeon7`); client maps it to a track URL via `MUSIC_TRACKS`. Falls back to `BIOME_MUSIC[biome]` if no music field. Exposes `MusicPlayer.start()`, `.stop()`, `.toggle()`, `.isPlaying()`, `.setRoom(roomId, biome, music)`. Auto-starts on login, toggled with M key.
- **`client/title.js`** — NES Zelda-style canvas-rendered title screen. Renders at 240×176 virtual pixels, scaled 3× to 720×528. Scene: rocky cliff walls (brick pattern), twinkling stars, mountains, pine trees, waterfall (left), flickering torch (right), pixel-art sword with gleam, golden title frame. Text rendered at full resolution for crispness. Chapel music attempts autoplay on load, falls back to first user interaction. `TITLE.phase`: `"title"` → `"login"` (Enter/click reveals login card) → `"done"` (on `login_ok`). `TITLE.hide()` called from `net.js` on successful login.
- **`client/fx.js`** — Client-side juice/FX system. Particle system (capped at 100, `spawnBurst()` / `spawnParticle()`), screen shake (`triggerShake(intensity, durationMs)` via CSS transform — stronger shakes override weaker ones), hit pause (freezes game loop ~40-60ms on impact), sword slash arcs, floating damage numbers, damage vignette (red edge flash on hurt), monster death corpses (last death frame lingers until room exit, rendered by `renderCorpses()`), dust puffs on movement start, monster spawn pop (scale 0→1.15→1.0 with stagger), knockback dust trail. All FX state lives on `G` namespace. Effects triggered from `net.js` message handlers (`monster_hit`, `monster_killed`, `player_hurt`, etc.).

## Server (`server/`)

All server-side shared state lives on a `GameState` singleton (`game = GameState()` in `server/state.py`). Modules import `from server.state import game` to access rooms, players, monsters, etc. Import order avoids circular deps: `constants` → `state` → `models` → `net` → `rooms` → `validation` → `dungeons` → `quests` → `lifecycle` → `combat` → `debug_monsters` → `mud_server`. Combat uses lazy imports for lifecycle to break one remaining cycle.

- **`mud_server.py`** — Main entry point. `handle_move()`, `check_edge_exit()`, `check_guard_proximity()`, `handle_chat()`, `handle_connection()`, `process_request()`, `STATIC_FILES` dict, `main()`. Imports and orchestrates all `server/` modules. In debug mode (`DEBUG_MODE=1`), wraps `sys.stdout` with `_LogBroadcaster` to tee all print output to connected clients as `server_log` WebSocket messages.
- **`server/constants.py`** — All tile ID constants, `WALKABLE_TILES` set, `TILE_CODES` dict, direction constants (`DX`, `DY`, `OPPOSITE_DIR`), room dimensions, gameplay tuning constants.
- **`server/state.py`** — `GameState` class holding all mutable state as singleton `game`. Contains: rooms, guards, monster_templates, dungeon_templates (keyed by type_id), monster_stats, custom sprite/tile registries, players dict, room_monsters, room_cooldowns, room_hearts, room_projectiles, counters, event_log, log_file. Multi-dungeon fields: `active_dungeons` (type_id → DungeonInstance), `room_to_dungeon` (room_id → type_id reverse lookup). Per-type content: `content_libraries` (type_id → {rooms, monsters, tiles} ContentLibrary dicts), `deprecated_content` (type_id → {monsters, tiles} sets), `regen_tasks` (type_id → asyncio.Task). `is_walkable_tile()` method checks both static `WALKABLE_TILES` and `custom_tile_recipes`.
- **`server/models.py`** — `Player`, `Monster`, `Projectile` data classes. `Monster.__init__` reads stats from `game.monster_stats` and behaviors from `game.monster_behaviors`. Monster supports `width`/`height` for multi-tile monsters (default 1); `occupies(tx, ty)` checks if a tile is within the monster's footprint.
- **`server/net.py`** — `send_to()`, `broadcast_to_room()`, `players_in_room()`, `player_info()`, `broadcast_debug()`, `log_event()`. Core networking helpers used by all other modules. `broadcast_debug()` sends `debug_log` messages to all connected clients (fire-and-forget, safe from sync code).
- **`server/dungeon_types.py`** — `DUNGEON_TYPES` configuration dict and `ENTRANCE_TO_TYPE` reverse lookup. Each type defines: name, template_dir, layouts, music/boss tracks, biome, exit_room, entrance_exit, boss/treasure template IDs.
- **`server/rooms.py`** — `load_room_files()` and `load_dungeon_templates(directory, type_id)`. Reads `.room` files, populates `game.rooms`, `game.guards`, `game.monster_templates`, `game.dungeon_templates[type_id]`.
- **`server/validation.py`** — `validate_monster()`, `validate_tile()`, `register_monster_type()`, `register_tile_type()`. Validation constants for behavior conditions/actions, attack types. Tile validation checks `layers` array of `[colorKey, x, y, w, h]` rects.
- **`server/dungeons.py`** — `DungeonInstance` class (with `cell_assignments`, `resolved_rooms`, `custom_slots` shared pool for Stage 7 lazy resolution), `get_dungeon_for_room(room_id)` (O(1) lookup via `game.room_to_dungeon`), `async create_dungeon(type_id)` (reads from `DUNGEON_TYPES`, uses per-type libraries, ~50/50 precreated/custom split, shared custom slot pool capped at 15, only resolves entrance), `resolve_dungeon_room()` (synchronous — materializes a library entry into `game.rooms[]`; custom cells pick a random slot from the shared pool), `destroy_dungeon(instance)` (tears down instance, removes from `active_dungeons` and `room_to_dungeon`, runs daily deprecation only when all dungeons empty), `_run_content_deprecation(type_id)` (per-type deprecation: expires oldest 10% of rooms, deprecates oldest 10% of monsters/tiles), `start_background_regen(num_rooms, type_id)` / `_background_regen()` (per-type async background regen), `get_active_content_lists(type_id)` (per-type monster/tile lists for AI prompts excluding deprecated), `is_dungeon_room()` (checks `room_to_dungeon`), `dungeon_player_count(instance)`.
- **`server/lifecycle.py`** — `spawn_monsters()`, `get_room_monsters()`, `on_player_enter_room()`, `on_player_leave_room()`, `send_room_enter()`, `do_room_transition()`. Room lifecycle management. **Room transition safety**: during `do_room_transition()`, the player is temporarily removed from `game.players` so `game_tick` can't target them while between rooms. Player is re-added in a `finally` block after `send_room_enter` completes. Death respawn uses the same pattern but runs as a background task in `combat.py` (`_death_respawn`). `on_player_leave_room` accepts `skip_dungeon_teardown` to prevent premature dungeon destruction during intra-dungeon transitions. Dungeon room resolution is synchronous (no AI generation) — unresolved custom rooms resolve instantly from the library pool or a precreated fallback. Conjuring animation only plays when first entering the dungeon via stairs (not per-room).
- **`server/combat.py`** — `handle_attack()`, all `exec_*()` and `warmup_*()` action handlers, unified `game_tick()` loop. **Message batching**: all game state changes in the tick loop are synchronous — messages are collected as `("broadcast"|"send"|"death"|"guard_chat", ...)` tuples in a list and flushed via `_flush_messages()` after the entire tick completes. This prevents `await` from yielding control mid-tick (which caused dungeon teardown crashes and dead-monster attacks). `_apply_damage()` is the sync damage core. **`game_tick()`** is a single ~30Hz async loop that calls `_tick_players()`, `_tick_all_monsters()`, and `_tick_projectiles()` (projectiles use a time accumulator to maintain their ~150ms effective rate). **Death respawn** is a background `asyncio` task (`_death_respawn`) — sleeps for the animation delay, then respawns. Per-monster/per-projectile `try/except` in tick loops prevents one crash from freezing all monsters.
- **`server/quests.py`** — `NPC_HANDLERS` dict, `npc_handler` decorator, quest NPC interaction handlers (Amara, Priest, Smith, Barmaid).
- **`server/npc_chat.py`** — LLM-powered NPC conversations. When a player sends a chat message while within 2 tiles of an NPC, the message is routed to Claude Haiku with the NPC's personality (from `.room` file) and conversation history. Keeps last 10 exchanges per (player, NPC) pair, cleared on disconnect. Uses same CLI/API backend as `ai_generator.py`. 3-second cooldown per player. Responses capped at 100 chars. Falls back to static dialog on LLM failure. Logs NPC responses as `NPC_CHAT` events.
- **`server/debug_monsters.py`** — `DEBUG_MONSTERS` dict (7 test monsters with full sprite data), `handle_debug_spawn()`, `auto_register_debug_monsters()`. Supports `variant:<kind>` and `variant:<kind>:<tier>` syntax to create programmatic monster variants via `/debug_spawn`.
- **`server/variants.py`** — Programmatic monster variant system. `create_variant(base_monster, tier)` takes a full monster data dict and produces a stronger, hue-shifted recolor. 5 tiers (0–4): swift/keen, tough/hardened, elder/greater, ancient/dire, frenzied/void. Scales HP (up to 2.5x), damage (+0 to +3), walk_time reduced by speed_mult (up to 1.4x faster), reduces attack cooldowns (down to 0.6x). Hue-shifts all sprite colors, death sprite colors, and projectile `sprite_color` via `colorsys` RGB→HLS→RGB conversion. Tracks lineage via `based_on` field and `variant` tag. `get_monster_data(kind)` looks up full monster data from the library.
- **`server/behavior_engine.py`** — Consolidated monster AI state machine: rule evaluation, action resolution, and action execution in a single `BehaviorEngine` class. `init(apply_damage)` creates the module-level `engine` instance (called once by `mud_server`). `engine.tick_monster_state()` is the per-monster tick entry point: handles idle (rule evaluation), walking (delegates to combat.py walk progression), and warmup states (charging/teleporting/area). Rules are evaluated top-to-bottom; first match wins. Conditions: `player_within`, `player_beyond`, `player_in_range_line` (with `los`), `hp_below`, `hp_above`, `random_chance`, `always`. Actions: `move` (direction: random/player/away/patrol/cardinal), `hold`, `projectile`, `charge`, `teleport`, `area` — all with params inline in the rule. Warmup (ticks) delays execution while locking params; cooldown (ticks) prevents re-evaluation of a specific rule. Execution handlers (`_exec_charge`, `_exec_teleport`, `_exec_area`, `_exec_projectile`) and warmup handlers (`_warmup_charge`, `_warmup_teleport`, `_warmup_area`) live in the class. Adding a new action type requires changes only in this file: add a resolver to `_action_resolvers`, an exec handler to `_exec_handlers`, and optionally a warmup handler. `_apply_damage` is injected via constructor to avoid circular import with `combat.py`. Monsters without behavior data default to `[{"if": "always", "do": "move", "direction": "random"}]`.
- **`server/dungeon_layouts.py`** — Dungeon layout templates. Defines 11 Zelda-inspired 8x8 grid layouts (eagle, fortress, shield, hammer, lizard, dragon, demon, lion, death_mountain, skull, axe, crown). Each layout has a name, grid (X=room, .=empty), and entrance cell.
- **`server/content_library.py`** — Library system for AI-generated content. `LibraryEntry` dataclass with id/tags/data/permanent (permanent entries never expire or get deleted). `ContentLibrary` class with fixed capacity, placeholder slots, expiry of oldest entries (skips permanent). Persists custom entries to JSON (permanent entries loaded from source at startup). Free-form tags normalized on ingestion. Library capacities: rooms 79 (64p+15c), monsters 8 (4p+4c), tiles 14 (7p+7c).
- **`server/dungeon_content.py`** — Precreated dungeon content definitions. 4 permanent monsters (skeleton, bat, dungeon_slime, phantom), 1 boss monster (dungeon_warden — 2x2, 20HP, multi-phase behavior with charge/area/projectile attacks, custom death sprite), and 7 permanent tiles (DW, DF, PL, SC, BZ, MF, CF) defined as data dicts with full stats, sprites, behaviors, and tags. `register_precreated_types()` registers all monsters (including boss) and all 7 tiles into game registries at startup (sprites, stats, behaviors, tile recipes, walkability). `load_precreated_content()` populates monster/tile/room libraries with permanent entries. Room conversion: `_convert_room_template()` converts parsed .room templates (numeric tilemaps) to library-compatible data (string tile codes).
- **`server/ai_generator.py`** — Claude integration for procedural dungeon content. **Multi-step generation** using focused AI calls, each with its own system prompt and validation: `generate_monster_design()` (kind/tags/stats/behavior), `generate_monster_sprite()` (sprite art given the design), `generate_tiles()` (custom tile definitions), `generate_layout()` (room name/tilemap/monster placements). The orchestrator `generate_room()` rolls for 0-2 new monsters and 0-2 new tiles (based on library fullness + random chance), generates them first, then calls `generate_layout()` with the full inventory — flagging newly created content as preferred. Uses Claude Haiku (`claude-haiku-4-5-20251001`). **Two backends** controlled by `AI_BACKEND` env var: `"api"` (Anthropic SDK, needs `ANTHROPIC_API_KEY`, 15s timeout) or `"cli"` (shells out to local `claude` CLI, uses subscription, 10min timeout, unsets `CLAUDECODE` env var to avoid nested-session detection). Default is `"cli"`. Generic `_call_ai()` helper handles rate limiting, JSON parsing, markdown fence stripping, validation callbacks, auto-patching callbacks, and retry logic for all steps. **Auto-patching** fixes common AI mistakes: moves monsters to reachable walkable tiles, carves paths to disconnected doorways, deduplicates room names, clamps attack stats. **Focused validators**: `validate_tile_definition()`, `validate_monster_sprite()`, `validate_monster_behavior()`, `validate_layout()`. Backward-compat `validate_room_response()` wraps all four. Rate limiting (15/min, 600/day — higher limits since one room = multiple calls), token usage tracking persisted to `data/api_usage.json`. `generate_room()` returns same format as before: `{name, tilemap, new_tiles, new_monsters, monster_placements}`. Standalone test via `python server/ai_generator.py`.
- **`server/prompts/`** — AI prompt templates stored as plain text files, loaded by `ai_generator.py` via `_load_prompt()`. Placeholders use `{{name}}` double-curly-brace syntax to avoid collisions with JSON in the prompt text. **System prompts** (4 files): `monster_design_system.txt`, `monster_sprite_system.txt`, `tiles_system.txt`, `layout_system.txt`. **User prompt templates** (4 files): `monster_design_user.txt`, `monster_sprite_user.txt`, `tiles_user.txt`, `layout_user.txt`. Edit the `.txt` files directly to tweak prompts — no Python changes needed.

## World Data

- **`worldgen.py`** — Offline world generator. Creates ~104 `.room` files in `rooms/` directory. Defines 16x8 biome grid, builds MST connectivity graph, generates tilemaps with biome-specific features, places NPCs and monsters. Biome config consolidated in `BIOME_CONFIG` dict (base tile, border, decor, walkable tiles, music, monsters per biome). Run once with `python worldgen.py`.
- **`rooms/*.room`** — Room data files. Village rooms are hand-authored; overworld rooms are generated by `worldgen.py`. Plain text format with header (name, biome, music, exits), tilemap (2-char tile codes), and entity sections (NPCs, monsters). All rooms (village + overworld) are loaded from `.room` files at startup — there are no hardcoded room definitions in `mud_server.py`.
- **`rooms/dungeon1/*.room`** — Dungeon room templates (64 files). Same `.room` format but without exits (exits are auto-generated from layout adjacency at runtime). Used as a template pool — the dungeon instance system picks a random layout and assigns templates to cells.
- **`music/*.mp3`** — Twelve mp3 tracks: `village.mp3`, `tavern.mp3`, `chapel.mp3`, `overworld.mp3`, `dungeon_a.mp3`–`dungeon_g.mp3`, `boss1.mp3`. Served via URL routes `/music.mp3`, `/music_tavern.mp3`, etc. (mapped in `STATIC_FILES`).

## Protocol

JSON over WebSocket.
- Client → Server: `login` (name, description), `move` (direction), `attack`, `chat` (text), `ping`
- Server → Client: `login_ok` (color_index, hp, max_hp), `room_enter` (tilemap + players + guards + monsters + exits + biome + music + exit_direction + hp + max_hp + optional custom_sprites + custom_death_sprites + custom_tiles + optional dungeon_debug), `room_generating` (sent before lazy dungeon room resolution), `player_moved`, `player_entered`, `player_left`, `attack` (name, direction), `chat`, `dance`, `info`, `error`, `pong`, `monster_moved`, `monster_killed`, `monster_hit`, `monster_spawned`, `player_hurt` (name, hp, max_hp, x, y, knockback), `you_died` (x, y), `player_died` (name, x, y, color_index), `hp_update` (hp, max_hp), `heart_spawned` (id, x, y), `heart_collected` (id), `music_change` (music — null for silence, or track name to switch), `debug_log` (text — dungeon/deprecation/regen events, shown in client debug overlay), `server_log` (text — raw stdout lines, shown in server log sidebar panel)

## Game Systems Detail

### State
All in-memory on the `game` singleton (`server/state.py`). Players tracked in `game.players` dict (websocket → Player). Rooms loaded from `.room` files into `game.rooms` at startup (15x11 tilemaps). NPCs and monsters parsed into `game.guards` and `game.monster_templates`. State resets on server restart. An `game.event_log` list records joins, leaves, and chat messages (with timestamps); exposed via `GET /get-log` (auth-gated behind `ADMIN_PASSWORD` Basic Auth) which returns the log as plain text. `GET /clear-log` clears it (also auth-gated).

### World Map
112+ rooms total. Village (8 rooms): Town Square (center) connects to Blacksmith (north), Forest Path (south), Tavern (east), Old Chapel (west). Old Chapel → Chapel Sanctum (west). Forest Path → Clearing → overworld gate (ow_0_7). The overworld is a 16x8 grid of ~100 rooms across 9 biomes (forest, mountain, desert, swamp, graveyard, castle, plains, lake, river) plus 4 interior rooms (2 caves, oasis, witch hut). Tavern has stairs up to Tavern Upper Floor. The Clearing also has stairs down to the dungeon entrance.

### NPCs
NPCs defined in `.room` files via `npc Name X Y sprite dialog | personality` lines (sprite is the sprite type key, e.g. `guard`, `smith`, `priest`, `barmaid`, `amara`, `witch`, `ghost`, `ghost_knight`, `ranger`, `farmer`, `nomad`, `merchant`, `elder`, `fisher`). The `|` separator is optional — text before it is the static dialog, text after is the personality prompt for LLM conversations. Loaded into `game.guards` at startup. Each NPC has a name, position, sprite type, dialog line, and personality. NPCs are rendered client-side via `drawNPC(ctx, px, py, sprite, S)` which dispatches to the appropriate sprite function from `NPC_SPRITES` map. Players can't walk on NPC tiles. Walking adjacent triggers the NPC's dialog as a chat bubble (broadcast to room), with a 10-second per-player cooldown to prevent spam. **LLM conversations**: when a player sends a chat message within 2 tiles of an NPC, the message is routed to Claude Haiku via `server/npc_chat.py` — the NPC responds in character based on its personality, with conversation history. Quest-aware NPCs (Amara, Priest, Smith, Barmaid) have registered handlers in `NPC_HANDLERS` (`server/quests.py`) that override static dialog on proximity.

### Monsters
Monster templates defined in `.room` files via `monster kind X Y` lines, loaded into `game.monster_templates` at startup. Five built-in types: slime (forest/plains, 1HP, 1dmg), bat (cave/graveyard, 1HP, 1dmg, fast), scorpion (desert, 2HP, 2dmg), skeleton (graveyard/castle/dungeon, 2HP, 3dmg), swamp_blob (swamp, 1HP, 1dmg). **Multi-tile monsters**: monsters can have `width`/`height` > 1 (stored in `game.monster_stats`). All collision checks (sword hits, contact damage, projectile spawning, charge paths) use `monster.occupies(tx, ty)` for footprint-based detection. Movement uses `_can_move_to()` / `_is_walkable_multi()` to verify the entire footprint is walkable. Distance calculations use the closest occupied tile (clamped). Sprites render at `SCALE * max(w, h)`. The dungeon boss (dungeon_warden) is 2x2. Lifecycle: spawn when first player enters, despawn when all leave. **Monster state machine**: mirrors the player's state machine. `monster.state` is one of `"idle"`, `"walking"`, `"charging"`, `"teleporting"`, `"area"`. `monster.state_data` holds state-scoped variables. Behavior engine evaluates only when `state == "idle"` and `walk_time` has elapsed since last action. **Smooth monster walks**: moves are 1-tile walks with duration `walk_time` (seconds per tile). The 33ms walk tick loop handles midway commit (position update + contact damage at 50%) and walk completion (→ idle). Wire protocol: `monster_walk_started` (client starts interpolation), `monster_walk_complete` (client clears walk state). Existing `monster_moved` is kept for instant position updates (charges, teleports). `walk_time` replaces the old `tick_rate` — it's both the walk duration AND the behavior tick interval (lower = faster). Warmup actions (charge, teleport, area) set the corresponding state and count down ticks in the 250ms monster_tick loop. Built-in monsters default to random wander; custom monsters can have behavior rules with conditions, actions, warmup, and cooldown. Multi-HP monsters take multiple hits — server sends `monster_hit` on damage and `monster_killed` on death. Protocol messages: `monster_walk_started`, `monster_walk_complete`, `monster_moved`, `monster_killed`, `monster_hit`, `monster_spawned` (optionally carries `custom_sprites`/`custom_death_sprites`). Killed monsters have a 10% chance to drop a heart pickup. **Dynamic monster types** can be registered at runtime via `register_monster_type(data)` (`server/validation.py`) which validates and adds to `game.monster_stats`, `game.custom_sprites`, optionally `game.custom_death_sprites`, and optionally `game.monster_behaviors`. **Dynamic tiles** via `register_tile_type(data)` which validates and adds to `game.custom_tile_recipes` and tracks walkability in `game.custom_walkable_tiles`. Both have validation functions (`validate_monster()`, `validate_tile()`) that check stat ranges, sprite bounds, color formats, behavior rules, tile layer bounds, and grid coordinates. All walkability checks use `game.is_walkable_tile(tile)` which checks both the static `WALKABLE_TILES` set and `game.custom_walkable_tiles`. The `room_enter` message carries custom sprite/tile data to the client, which merges it into `customMonsterSprites`/`customDeathSprites`/`customTiles` registries. Client rendering uses generic `drawMonsterSprite()`/`drawMonsterDeath()` for all monster kinds (no hardcoded if/else chains). Custom tiles use `runTileRecipe()` interpreter. Chat command `/debug_spawn <kind>` spawns test monsters (7 built-in: fire_slime, ice_bat, shadow_skull, skeleton_archer, ghost_teleporter, war_boar, flame_mage; also works with any registered or built-in kind). **Monster variants**: `/debug_spawn variant:<kind>` or `/debug_spawn variant:<kind>:<tier>` creates a programmatic variant — a stronger, hue-shifted recolor of the base monster. 5 tiers (0=swift to 4=frenzied) scale stats and shift all sprite/projectile colors. Variants track lineage via `based_on` field. See `server/variants.py`.

### Monster Behavior Engine
Rule evaluation with warmup/cooldown, driven by the monster state machine. Each monster has `walk_time` (seconds per tile — lower = faster). Behavior engine evaluates only when `state == "idle"` and `walk_time` has elapsed. Rules evaluate top-to-bottom; first match wins. Returns `{action, warmup, cooldown, ...params}`. **Conditions**: `player_within` (Manhattan range), `player_beyond`, `player_in_range_line` (same row/column, optional `los` for line-of-sight), `hp_below`, `hp_above`, `random_chance`, `always`. **Actions**: `move` (with `direction`: `random`/`player`/`away`/`patrol`/cardinal — always 1 tile, speed controlled by walk_time), `hold`, `projectile` (direction + damage + sprite_color), `charge` (direction + range + damage), `teleport` (target: player/random/away + drift + range + damage), `area` (range + damage). **State machine** in `combat.py` handles transitions: `move` → `start_walk()` (walking state, 33ms tick loop handles midway commit + completion), `charge`/`teleport`/`area` with warmup → corresponding state (countdown in 250ms loop, execute on completion), `projectile`/`hold` → instant execute, stay idle. **Warmup** (ticks): delays execution; monster enters charging/teleporting/area state; parameters locked at warmup start. Used for telegraphed attacks — charge gets `charge_prep` message, area gets `area_warning`, teleport gets `teleport_start` (monster becomes intangible). **Cooldown** (ticks): after execution, this rule is skipped for N ticks. `stats.damage` is contact-only; each attack rule carries its own `damage`. Example: `{"if": "player_in_range_line", "range": 6, "los": true, "do": "projectile", "direction": "player", "damage": 1, "sprite_color": "#ff0000", "warmup": 1, "cooldown": 5}`. Projectiles tracked per-room in `game.room_projectiles` dict and moved by `projectile_tick()` async loop. Protocol messages: `monster_walk_started`, `monster_walk_complete`, `projectile_spawned`, `projectile_moved`, `projectile_hit`, `projectile_gone`, `charge_prep`, `monster_charged`, `teleport_start`, `teleport_end`, `area_warning`, `area_attack`.

### Player Health
Players have 6 HP (displayed as 3 hearts in HUD). Contact damage occurs when a player walks onto a monster or a monster hops onto a player — damage amount varies by monster kind. On damage: 1.5s invincibility frames (client flickers sprite), knockback away from facing direction, red flash overlay. At 0 HP: death animation (spin + fade to black + "You died!"), then respawn at Town Square after 5.5s delay with full HP. Death respawn runs as a background asyncio task (`_death_respawn` in `combat.py`) — the player stays in `game.players` at 0 HP during the animation delay, then is temporarily removed during the room swap. `handle_move` guards heart pickup and NPC proximity with `if player.hp > 0`. The Barmaid NPC in the tavern heals players to full HP.

### Heart Pickups
When a monster is killed, there's a 10% chance it drops a heart on its tile. Hearts bounce on the ground and restore 2 HP when walked over. Hearts are tracked per-room in `game.room_hearts` and cleaned up when all players leave.

### Dungeons

Library-managed dungeon instances (Stage 7). **Multi-dungeon architecture**: multiple dungeon types supported via `server/dungeon_types.py` `DUNGEON_TYPES` dict. Each type config has: layouts, music/boss tracks, biome, theme (for AI generation), exit room, wall tile, entrance exit, boss/treasure template IDs, and optional per-type library capacities. State: `game.active_dungeons` (type_id → DungeonInstance), `game.room_to_dungeon` (room_id → type_id for O(1) lookup), `game.content_libraries` (type_id → {rooms, monsters, tiles}), `game.deprecated_content` (type_id → {monsters, tiles}). Use `get_dungeon_for_room(room_id)` to find the instance for any room. Room IDs are `{type_id}_{col}_{row}` (e.g. `d1_3_3`, `d2_0_1`). Content libraries are per-type with files at `data/{type_id}_*_library.json`.

**Dungeon types**: d1 = Dark Dungeon (8x8 layouts, 64 rooms, DW/DF tiles, entrance in `clearing`), d2 = Water Temple (3x3 layouts, 7 rooms, TW/TF/CR/WA/SH tiles, entrance in `forest_path`). Wall tile for unused exits is configurable per type. Water temple rooms have ambient mist FX (client-side, triggered by `dungeon_type` field in `room_enter`).

**Lazy resolution**: only the entrance room is resolved at creation time; other rooms are materialized into `game.rooms[]` synchronously when a player first enters them. Custom cells draw from a shared slot pool — filled slots use existing library content, empty/exhausted slots fall back to a precreated room (no JIT AI generation). A conjuring animation (2.5s, fade-from-clearing with torchlight/particles/text) plays when first entering the dungeon via stairs; individual room transitions within the dungeon are instant. `DungeonInstance` tracks `cell_assignments` (source, entry, resolved status) and `resolved_rooms`.

**Dungeon path**: at creation, a randomized DFS spanning tree connects all cells, plus ~25% extra edges for non-linearity. The furthest leaf node from the entrance becomes the **treasure room** (guaranteed dead end with 1 connection), and the cell leading to it becomes the **boss room**. Both special templates are excluded from the regular library pool (filtered in `dungeon_content.py`). Exits between dungeon rooms are computed from the connection graph (not raw adjacency); unused exits are walled off. `DungeonInstance` stores `connections` (set of frozensets), `boss_cell`, and `treasure_cell`. Cleared rooms (all monsters killed) don't respawn.

**Boss system**: Boss monsters have `"boss": True` in stats. Boss detection uses `monster.is_boss` — not hardcoded to a specific kind. Boss music is randomized from `DUNGEON_TYPES[type_id]["boss_tracks"]`, stored as `DungeonInstance.boss_track`. **Boss choir overlay**: when a player hits any boss, an ethereal choir track plays for all other dungeon players, volume scaled by BFS distance from boss room. Managed via `boss_engaged` on `DungeonInstance` (reset on boss death). Choir track is dynamic — matched to the randomized boss music (e.g. boss2 → music_boss2_choir.mp3), sent via `choir_track` field in `boss_choir_start` messages. Boss death: server broadcasts `music_change` with null music; client triggers `bossDeathEffect` (white flash, screen shake, particle explosion).

**Dungeon items (Map & Compass)**: Each dungeon instance places a Map and Compass in two random non-special cells. Items are placed on reachable walkable interior tiles at room resolution time. Per-instance state: `instance.item_cells`, `instance.dungeon_items`, `instance.collected_items`. Once ANY player picks up an item, ALL dungeon players benefit. Map reveals minimap; Compass adds boss room marker and blinking player dot. Items reset when dungeon is destroyed. Pickup triggers hold-item animation (2.5s freeze, item floats above head with golden glow and sparkles via `drawItemPickupOverlay`). Client state: `G.dungeonState`, `G.dungeonGroundItems`, `G.itemPickupActive`, `G.itemPickupEffects`.

**Daily deprecation**: when a dungeon is destroyed (all players leave), if 24+ hours have passed since last pass: oldest 10% of custom rooms expired; oldest 10% of custom monsters/tiles deprecated (excluded from AI prompts but kept in registries). **Background regen**: after deprecation, a background asyncio task generates replacement rooms to refill expired slots. Snapshots library state synchronously; async task works from snapshot only. Results applied synchronously (no `await` during apply). Libraries persisted to `data/*.json`.

### Music
MP3 tracks organized in `music/` subdirectories (`overworld/`, `dungeon1/`, `dungeon2/`). Each `.room` file specifies a `music` field; server sends it in `room_enter`; client maps to track URL via `MUSIC_TRACKS`. Fallback: `BIOME_MUSIC[biome]`. Toggled with M key. **Silence**: `MusicPlayer.silence()` fades out and records `silencedBiome`; `setRoom` skips playback while in the same biome. Used for post-boss-defeat silence. **Boss choir overlay**: when a player hits a boss, choir track plays for other dungeon players, volume scaled by BFS distance from boss room.

### Movement

**NES Zelda-style half-tile free movement**: players move continuously while keys are held, at `PLAYER_SPEED=4.0` tiles/sec. Positions are sub-tile floats. Axis alignment: switching direction smoothly snaps the perpendicular coordinate to the nearest half-tile. Wall overlap: collision only checks the bottom half of the 1×1 hitbox (`y+0.5` to `y+1`), so sprite heads can overlap walls (NES Zelda style). `_is_position_walkable()` checks all tiles overlapping the bottom-half hitbox. Client collision uses the aligned (snap-target) half-tile for the perpendicular axis, so players can slip through 1-tile gaps even when slightly misaligned (NES Zelda corner-nudge). Movement blocked during dungeon conjuring animation (`G.conjuring`). Monsters still use the old tile-to-tile walk system (`WALK_TIME`).

**Client player state machine**: `G.state` is an enum (`"idle"`, `"attacking"`, `"dying"`) with `G.stateData` holding state-scoped variables (replaced on every `setState()` call). Movement happens continuously in `"idle"` while direction keys are held — `playerTick()` computes local movement, collision, and position reporting each frame. Attacks are optimistic (animation starts immediately, server handles hit detection via float AABB overlap — sword is a 1×1 hitbox at `player.x+dx, player.y+dy` vs monster footprint). Holding space chains attacks. Reconcile messages hard-reset to idle and snap `preciseX/Y`.

### Networking Model

Server-authoritative with client-side prediction for movement. Client moves locally at 60fps and reports to server when `Math.round(precisePos * 2) / 2` changes (i.e. the nearest half-tile snaps to a new value — triggers at 0.25 past each half-tile boundary). Client sends `position_update` with snapped `{x, y, direction}`. Server validates: half-tile snapped, rate limit (`POSITION_UPDATE_RATE`), distance (`MAX_MOVE_PER_UPDATE`), walkability, guard collision. On accept: updates `player.x/y`, relays `player_walk_half` to other clients (excluding sender). On reject: sends `reconcile` with server position. Other clients receive `player_walk_half` and animate a smooth interpolation over `HALF_WALK_TIME_MS` (125ms). All sync is scoped per room; players only receive messages about their current room.

### Emotes
`/dance` makes the player do a looping boogie animation (4 frames). Dance stops when the player moves. Dancing state is synced — new players entering a room see ongoing dances.

### Combat

Space bar triggers a sword stab attack (NES Zelda-style). The attack is a 2-frame animation (~300ms) that draws a thrust pose on the player and a sword on the adjacent tile in the facing direction. Player movement is frozen during the attack. Server enforces a 0.4s cooldown. Sword hit detection uses float AABB overlap (1×1 hitbox at `player.x+dx, player.y+dy` vs monster footprint). All entity collisions (monsters, hearts, items, guards, projectiles) use float AABB overlap.

**Knockback**: On damage, player is knocked back 1 tile (snapped to half-tile) away from damage source. Direction uses **previous positions** (before overlap) for contact damage, current positions for projectile/area/charge damage. Fallback: push away from facing direction if delta is zero. 200ms client-side hitstun (`G.stunUntil`) freezes controls. Monster contact collision uses interpolated walk position (`_get_monster_visual_pos`) not just committed tile.

**Collision grace period**: Contact damage uses a 100ms buffer (`COLLISION_GRACE_PERIOD`) for corner-scrape forgiveness. First AABB overlap records a pending collision on `player.pending_collisions` (keyed by `id(monster)`). `_resolve_pending_collisions()` in `game_tick()` re-validates before applying damage. Prevents false hits when player and monster slide past each other.

**Collision debug overlay** (debug mode, backtick toggle): `G.debugCollision` shows player AABB (green, bottom-half bright), monster AABBs (red), and 5-second hit ghosts with pre-knockback player (cyan), source AABB (red), knockback destination (yellow dashed), direction delta (orange arrow). Server sends `debug_*` fields in `player_hurt` messages.

### NPC Gifts

NPCs can give items to players through AI dialog. Room file format: `npc Name X Y sprite Dialog | Personality | Item Name:condition text`. The third `|` section is optional. Gift tracking flags are auto-generated as `gift_{room}_{npc}_{item}` for uniqueness. Special item effects (sword animation, heart container HP boost) are mapped in `GIFT_EFFECTS` in `npc_chat.py` by display name. The AI includes `[GIVE_ITEM]` in its response when it judges the condition is met (same pattern as `[CALL_GUARDS]`).

### Monster Death Sprites

4-frame death animations in `data/monsters.json` under `death_sprite`. Frame 4 is a visible corpse/remains (not a vanishing fade). AI prompt (`monster_sprite_system.txt`) requests `death_sprite` alongside `sprite`. Fallback: generic splat from the monster's primary color if no death sprite exists. Corpses rendered by `renderCorpses()` in `fx.js`, cleared on room enter.

### API & Prompt Caching

API path uses prompt caching — system prompts marked with `cache_control: {"type": "ephemeral"}` for 5-minute caching. `UsageTracker` tracks cache write/read tokens separately with accurate cost multipliers (1.25x write, 0.10x read). `dungeon_content.py` declares which monster/tile IDs are permanent members of each dungeon's content library (ID lists only — all recipes live in `data/monsters.json` and `data/tiles.json`). Precreated content is per-type via `PRECREATED_CONTENT` dict.
